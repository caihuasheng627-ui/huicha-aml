## 1. 代码里的产品定位：告警后调查 Copilot

一句话（与 `README.md` §1 一致）：**上游检测已经产生告警；本系统不替代监测引擎，只把告警升级为案件，出受控调查底稿，由人签发。**

设计原则（`/api/health` `contest.headline`）：**AI 负责推理，规则负责边界，证据负责事实，人负责最终决策。**

### 1.1 代码实际做的事

本地可演示的 **Case Workspace**（`huicha-aml/frontend/src/`）：

1. 从告警列表选案（或实验室快捷键打开路演案）。
2. 点「开始调查」：`GET /api/alerts/{id}/investigate/stream`（失败回落 `POST .../investigate`）。
3. 工作台并排看：规则对照 / AI Judge / 护栏后建议、证据图谱、流水、反事实、被拒绝 Claim、法规摘录、补证清单。
4. 调查员 `submit` → 复核岗 `confirm` / `modify` / `reject`（`POST /api/alerts/{id}/decide`）。
5. 导出 Markdown 底稿（标题写明**非报送报文**）。

入口与编排：

| 层 | 路径 | 做什么 |
| --- | --- | --- |
| HTTP | `huicha-aml/backend/app/main.py` | 告警 CRUD、调查、双控签发、导出、健康检查 |
| 门面 | `huicha-aml/backend/app/agents.py` `run_investigation` | 绑工具审计，注入 Judge/Reporter/知识库依赖 |
| 流水线 | `huicha-aml/backend/app/pipeline/runner.py` | 按 `STAGES` 顺序跑，SSE 推 `stage` 事件 |
| 人签（调查之后） | `huicha-aml/backend/app/workflow.py` | 分岗、`can_sign` 阻断，**不跑调查** |

### 1.3 代码明确不做的事（写 §五/§六 时必须保留）

| 不做 | 代码依据 |
| --- | --- |
| **不替代监测引擎** | 告警入库字段 `upstream` 默认「规则引擎模拟告警」（`models.py`）；种子写「规则引擎：…」。流水线只调查已有告警。 |
| **不自动报送 STR / 不连监测中心** | 无报送端点、无 XML/报文组装。护栏恒触发 `human-approval` / `effect: 禁止自动报送`（`decision.py`）。导出标题「可疑交易调查草稿（**非报送报文**）」（`main.py`）。`schema.py`：`Agent 不得自动上报`。decide/note 回包：「系统不会自动报送」。 |
| **不把规则分与 AI 分加权合成** | 见 §3。旧 Challenger 调分函数 `llm.enrich_challenger` **无调用方**。 |
| **不在无人签时把案件变成已报送** | 状态机只到 `ready_to_file` / `closed` / `monitoring`；没有「已报送」动作。 |
| **不接真实核心 / 不是银行 SSO** | `security.py` 文件头写明竞赛原型；演示账号 `002183` / `002201`。SQLite 调查载荷明文。 |
| **不做在线再训练** | `/api/metrics` 注释：竞赛原型不做在线再训练。 |
| **不宣称生产准确率** | `/api/health` `limitations`；`data_note: synthetic`。 |

结论三档（内部标签 → 界面 → 建议动作；Agent **不得执行**报送）：

| 内部 | 界面（`analyst_rules.CONCLUSION_LABEL`） | 建议动作 |
| --- | --- | --- |
| `exclude` | 排除 | CLOSE |
| `observe` | 继续观察 | MONITOR |
| `suggest_report` | 建议上报 | `REPORT_REVIEW`（须人签） |

`confidence` 字段标记为 `llm_self_assessed_not_calibrated`（或消融时 `rule_score_not_calibrated`）。**不是准确率，不是校准风险概率。**

## 2. 端到端调查流水线（以后端 STAGES 为准）

### 2.1 顺序（写架构图用这一份）

```
POST/SSE /api/alerts/{id}/investigate
  → agents.run_investigation
    → pipeline.runner.run_pipeline
      → Planner → Collector → Privacy → Analyst
        → Judge → Skeptic → Reporter → Guardrail → Assemble
          → state.payload（含 can_sign / sign_blockers）
```

权威顺序在 `huicha-aml/backend/app/pipeline/stages/__init__.py`：

```
PlannerStage, CollectorStage, PrivacyStage, AnalystStage,
JudgeStage, SkepticStage, ReporterStage, GuardrailStage, AssembleStage
```

**两处不要抄错：**

1. **前端进度条**（`InvestigateFlow.jsx`）把 Analyst 画在 Privacy 前面，且把 Judge 标成「慧查agent」、不单独画 Guardrail/Assemble。那是演示动画，**不是后端执行序**。后端 Privacy 在 Analyst **之前**建 `PrivacyMap`；Guardrail 在 Reporter **之后**，才能读到 `fact_issues`。
2. **历史名 Challenger**：查询参数仍叫 `use_challenger`。在 V3 里它的意思是「开慧查agent」（Judge LLM + Skeptic 反事实重跑 Judge + 条件 Reporter LLM），**不是**旧的调分 Challenger。payload 固定 `"challenger": []`。`llm.enrich_challenger` 只定义、无调用。

`use_challenger=false`（实验/消融）：Judge 用规则对照合成对象（`score_kind: rule_only_ablation`），不跑 Reporter LLM，不跑反事实搜索，可靠性强制 `committed`。

`experiment_mode` 只写入 payload/审计，**不改变阶段逻辑**。

### 2.2 各阶段：职责 / 输入输出 / 硬禁止

#### Planner — `pipeline/stages/planner.py`

| | |
| --- | --- |
| 职责 | 按告警类型选只读工具子集；从 DB 填最小 `state.alert` |
| 输入 | `alert_id`，`Alert.alert_type` |
| 输出 | `state.planned`，`state.alert` |
| 实现 | `tools.plan_tool_names`：关键词规则，**不调 LLM** |
| 硬禁止 | prompt `planner_v2`：「只规划只读工具步骤，不判断风险，不编造账号。」不打分、不报送。 |

工具白名单 `tools.ALLOWED_TOOLS`：`get_alert` / `get_customer` / `get_accounts` / `get_transactions` / `get_related_accounts` / `get_network` / `get_graph` / `get_timeline` / `get_baseline` / `check_watchlist` / `search_knowledge` / `search_regulation`。无写核心、无删数、无报送工具。

规划规则摘要：基础七件套必有；含「大额/频繁/夜间/转账」加基线与图谱；含「拆分/归集/名单/团伙」加对手与名单；含「观察/亲属」加基线、图谱、关联账户。

#### Collector — `pipeline/stages/collector.py`

| | |
| --- | --- |
| 职责 | 执行计划：`collect_bundle` 取告警/客户/窗口流水；知识库检索；可选一度对手扩窗（≤4 个 peer） |
| 输入 | `planned`，`alert_id`，`search_knowledge` |
| 输出 | `bundle`，`alert`，`customer`，`txs`，`kb_hits`，`timeline`，`account_id`，`as_of` |
| LLM | 无 |
| 硬禁止 | 只跑白名单工具；不改处置结论；不编造流水。窗口全量进 bundle；**抽哪笔进模由 Analyst/sampler 决定，不由模型决定**。 |

#### Privacy — `pipeline/stages/privacy.py` + `privacy.py`

| | |
| --- | --- |
| 职责 | 从 bundle 建 `PrivacyMap`（`privacy_v2`） |
| 输入 | `bundle` |
| 输出 | `state.privacy` |
| 硬禁止 | 进模丢掉 `city/phone/mobile/id_number/id_card/legal_id`；姓名→`CLIENT_001`，账号→`ACCOUNT_001`，客户号→`CUST_001`；`TX-*` 不替换（供引用）。`prepare_for_llm` 后 `assert_clean`，泄漏抛 `PrivacyLeakError`（调查 API 502）。`inspect_outbound` 拦截未脱敏 `6222-*`。工作台仍显示受控明文；**只有 LLM 出站脱敏**。SQLite 载荷仍明文。 |

#### Analyst — `pipeline/stages/analyst.py` + `analyst_rules.py` + `sampler.py` + `evidence.py`

| | |
| --- | --- |
| 职责 | 确定性指标与规则对照；抽进模样本；建 Evidence Graph；算允许引用集合 |
| 输入 | bundle / txs / kb / customer |
| 输出 | `analyst`，`findings`，`baseline_result`（`rule_baseline`），`sampling`，`llm_findings`，`ev_graph`，`allowed_*` / `cite_set` |
| LLM | 无 |
| 硬禁止 | 模块头：「规则分仅作为透明对照。」`rule_baseline`：「不读取上游告警标签加分，也不决定最终建议。」`evidence.py`：「禁止 LLM 创造节点。」`sampler.SAMPLE_CAP = 30`：模型只见样本/簇代表，基线合计来自窗口全量。 |

`analyst_rules.rule_prior()` 仍在文件里，**assemble 未接线**，payload 里 `rule_prior` 恒为 `0.0`。不要写成「规则先验已并入最终分」。

#### Judge（界面称慧查agent）— `pipeline/stages/judge.py` + `decision.py` + `llm.py` + `prompts.py`

| | |
| --- | --- |
| 职责 | 输出结构化三档：`disposition` / `confidence` / `typologies` / `supporting_evidence_ids` / `contradicting_evidence_ids` / `missing_evidence` / `rationale[]` / `next_actions`；`normalize_judge` + `verify_judge` |
| 输入 | 样本流水、压缩 findings、`prompt_allowed`、`cite_set`、privacy、可选修复 issues |
| 输出 | `judge`，`judge_validation`，`conclusion`，`confidence`，`fallback_reason` |
| LLM | `use_challenger=true` 时 `enrich_judge`；`HUICHA_JUDGE_TOOLS=1` 时 `pipeline/toolkit.py` 最多两轮只读补证（锁定本案 `account_id`，跨账户拒绝） |
| 硬禁止 | 上游告警只是待复核线索；不得编造事实；引用必须在 `allowed_evidence_ids`；`missing_evidence` 只写中文材料名，禁止塞编号；交易模式理由须带封闭谓词（`judge_v3p`）。校验失败先修复一轮，再失败则降级规则对照且 `passed=false`。 |

`HARD_CONTRACT_KINDS`（`decision.py`）：`empty_rationale` / `uncited_rationale` / `invalid_citation` / `missing_rationale` / `missing_support`。行级谓词：`missing_predicate` / `predicate_failed`。

封闭谓词目录（`predicates.py` `PREDICATES`）：金额严格递减/递增、连续过桥 A→B→C、有界时间窗、接近 5 万阈值、对手前缀、夜间（21:00–06:00）、渠道一致、账户数下限。后端在本案快照上**重执行**，不信模型口头。

#### Skeptic（不是独立「Challenger 模型」）— `pipeline/stages/skeptic.py`

| | |
| --- | --- |
| 职责 | 确定性：已核验谓词 claims；有界反事实最小证据搜索；可靠性/弃权 |

## 3. 人机分工：规则 vs LLM（确认：不加权合成）

**结论（写 §六必须用）：V3 主路径里，规则对照分与 AI 自评把握度不相加，也不做加权合成最终建议。**

### 3.1 谁做什么

| 机制 | 阶段 | 决定什么 |
| --- | --- | --- |
| 确定性规则 | Planner / Collector / Privacy / Analyst / 抽样 / Evidence Graph / 谓词执行 / 事实回查 / Guardrail / Assemble / 补证清单 | 取数范围、进模样本、对照分、引用是否合法、政策升级、能否签发 |
| LLM | Judge（及反事实再调用）；条件满足时的 Reporter | 三档建议 + 证据列表 + 四段正文润色 |
| 人 | `workflow.assert_decision_allowed` | 提交复核、签发、改签、退回；对处置负责 |

### 3.2 不相加的代码锚点（可直接贴脚注）

`decision.rule_baseline`：

> 规则只提供透明对照，不与 AI 分数合成。  
> note：仅按本案流水重新计算的规则对照，不读取上游告警标签加分，也不决定最终建议。

`decision.apply_guardrails`：

> 规则只作不可绕过的政策边界，不参与加权打分。  
> note：护栏仅执行政策否决/升级，不与模型做加权合成。

`assemble.py` `scoring`：

```
base = 规则对照分
rule_prior = 0.0
llm_delta = 0.0
raw/final = Judge confidence
mode = "judge_not_additive"
note = "规则对照与 AI 自评把握度不相加。"
```

最终 `risk.conclusion` 来自护栏后的 `state.conclusion`（Judge disposition ± 名单升级），**不是** `risk.aggregate(..., challenger_delta)`。后者仍在 `risk.py`，主调查路径不用。

Analyst 内部会给模式/名单等加规则分（如拆分 +0.38），那只进入 `baseline_result.score` 作对照，并经旧阈值 `score_to_conclusion`（&lt;0.35 排除 / &lt;0.55 观察 / 否则建议上报）得到**对照档**，不覆盖 Judge。

弃权不改档：`reliability.compute_reliability` 只把 `stance` 设为 `abstain`，从而 `can_sign=false`。软/硬理由**都会**阻断直接签发。

工作台并排三列：规则对照 / AI Judge / 护栏后建议。分歧交给人，不在后台揉成一个分。

## 5. 签发阻断码（`can_sign` / `sign_blockers`）

权威计算：`assemble.py` 的三合取 + `workflow.collect_sign_blockers`。前端 `signBlockers.js`：**若后端已给 `sign_blockers` 数组，原样使用**；否则才本地重算。

### 5.1 产品逻辑会写入 `sign_blockers[].code` 的全部码

| code | 严重度（reliability） | 中文 message（代码原文） | 含义 |
| --- | --- | --- | --- |
| `fact_check` | 仅签发层 | 事实回查未通过 | 报告硬事实问题非空 |
| `judge_fallback` | hard | 慧查agent 已降级为规则对照，不能直接签发 | LLM 失败或 `score_kind==fallback` |
| `predicate_failed` | hard | 可执行谓词未通过核验，不能直接签发 | 封闭谓词在快照上为假 |
| `missing_predicate` | hard | 交易模式理由缺少可执行谓词，不能直接签发 | 纯 TX 理由未填 predicate |
| `citation_failed` | hard | 证据契约未通过，不能直接签发 | 空/无引用/非法编号/缺支持等 |
| `cf_invalid` | hard | 反事实轮次输出无效，且未形成可依赖的证据核心，不能直接签发 | CF 未通过且无 necessary_ids |
| `rule_judge_conflict_low_conf` | soft | 规则对照与 AI 建议分歧且自评把握度偏低，系统弃权 | 对照档≠Judge 档且 confidence&lt;0.55 |
| `cf_not_dependent` | soft | 建议上报未形成对其声明证据的依赖，系统弃权 | 上报档 CF 通过但无必要证据 |
| `evidence_core_unverified` | soft | 有界证据搜索未形成稳定核心，系统弃权 | sufficiency.verified=false；**双方都是排除时不触发** |
| `judge_contract` | 汇总兜底 | `judge_validation.reason` 或「证据契约未通过」 | validation 失败且尚未有 citation/predicate/fallback 码 |
| `abstain` | 兜底 | 当前结论不可直接签发 | reliability 行缺 code |

软/硬都会让 `stance=abstain` → `can_sign=false`。软不是「可以签发」。

### 5.2 相关但不是 `sign_blockers` 的码

| code | 位置 | 含义 |
| --- | --- | --- |
| `human-approval` | 护栏 checks | 任何建议均须人工签发 / 禁止自动报送 |
| `watchlist-no-close` | 护栏 | 名单命中不得直接排除 |
| `fact-check-block` | 护栏 | 事实回查失败不得签发（政策行；签发层对应 `fact_check`） |

校验 `issues[].kind`：`empty_rationale` / `uncited_rationale` / `invalid_citation` / `missing_rationale` / `missing_support` → 通常映射 `citation_failed`；`predicate_failed` / `missing_predicate` 同名；`judge_failure` / `invalid_output` → `judge_fallback`。

### 5.3 双控矩阵（写「人负责」用）

| 条件 | 调查员 submit | 复核 confirm | 复核 modify |
| --- | --- | --- | --- |
| `can_sign=true`，已调查 | 可 | 须已 submit | 须已 submit |
| `can_sign=false` | 须填说明 | **400 不能签发** | 须填修改说明 |
| 尚未 submit | — | 400 | 400 |
| 岗错 | confirm→403 | submit→403 | — |
| 提交人=复核人 | — | 403 | 403 |

## 8. 与三类方案的一句事实对照（写 §六差异化）

**vs 监测 / 检测引擎：** 本仓库只消费已入库告警（`upstream` 为模拟规则引擎），Judge 把告警当作待复核线索且不把告警类型加进结论分；没有 AUC、没有在线监测循环，也没有替代上游规则/模型的训练代码。

**vs 通用大模型聊天：** 调查输出必须经过 `verify_judge` 引用/谓词契约、有界反事实、`fact_check`、政策护栏和 `can_sign`，工具仅白名单只读，出站走 `PrivacyMap`；没有「一段 prompt 直接给结论并可签发」的路径。

**vs 调查手册 / 纯人工底稿：** 手册要素（触发点、资金行为、疑点、理由、法规转述）由 Reporter 填进四段草稿并导出为「非报送报文」，人仍按双控提交/签发；系统不自动生成监测中心报文，也不在无人确认时关闭案件为已报送。

（旧加权 Challenger、规则先验并入总分、向量 RAG、银行 SSO、自动 STR——代码里要么未接线，要么明确禁止。）
