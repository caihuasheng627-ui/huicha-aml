## 第五节　AI 技术架构

### P0　流水线顺序与「谁抽 30 笔」

- **表 4 / 图 3 把 Policy Guardrail 画在 Reporter 之前。**  
  代码 `STAGES` 是 `Judge → Skeptic → Reporter → Guardrail → Assemble`（`huicha-aml/backend/app/pipeline/stages/__init__.py`）。护栏要消费 Reporter 的 `fact_issues`，不能先于成稿。  
  `figures/fig_pipeline.drawio` 同样画成 Skeptic→Guardrail→Reporter，与代码不一致。计划书应改成代码顺序，或加一句「图为逻辑分组，执行上成稿后才跑事实闸」。

- **表 4 写 Collector「抽出不超过三十笔代表样本」。**  
  Collector 只按窗口取全量（及可选一度对手流水）。`SAMPLE_CAP=30` 在 **Analyst** 调用 `sampler.select_for_judge`（`pipeline/stages/analyst.py`、`sampler.py`）。应改到 Analyst 行，Collector 行改为「取窗口全量，基线合计来自全量」。

- **「进模前脱敏」容易被理解成 Privacy 段已经把工作台数据改成占位符。**  
  Privacy Stage 只 `PrivacyMap.build_from_bundle`。工作台/SQLite 仍是明文；占位符替换发生在 `llm.prepare_for_llm`（Judge/Reporter 出站）。应写清「仅 LLM 出站脱敏」。

### P1　角色名、模型与规则分工

- **产品 Judge prompt 不是 v3 也不是实验里的 v4。**  
  `prompt_version("judge")` 返回 **`judge_v3p`**（在 v3 三档标准上增加可执行谓词 `predicate`/`args`）。第五节写「研判走大模型」时请点名 `judge_v3p`；`judge_v4` 只出现在实验消融。旧审计报告 / `REAL_MODEL_REPORT.md` §10 仍写默认 `judge_v3`，**不要抄文档、要抄 `prompts.py`**。

- **Skeptic 不是独立 LLM Agent。**  
  表 4「质疑」易被听成第二个模型在质询。实现是：Judge 段已做 `verify_judge`；Skeptic 段做有界删证据后**重跑同一 Judge** + `compute_reliability`。`skeptic_v1` 字符串不送模型。应改成「确定性引用/谓词核验 + 反事实重跑 Judge」。

- **Planner 不是智能体规划。**  
  正文已有「规划器为确定性白名单」，表 4 保持即可；口播/PPT 不要说「多智能体自己决定调什么工具」。

- **Assemble「全部校验通过才允许人工签发」写过头。**  
  `can_sign=false` 时：复核岗 **不能** `confirm`；但调查员可带说明提交，复核岗可带说明 `modify`（修改后签发）。签发后仍是已签草稿、不是已报送。建议改成：「直接同意签发须 `can_sign`；人可在写明理由后修改签发或退回。」

- **「LLM 输出被截断或非 JSON 时降级到规则对照」** 基本正确，但漏了：先带 `repair_issues` 重试一次；截断不写缓存；降级后 `reliability` 为弃权，**不能直接同意签发**（不是静默用规则分冒充 AI 结论）。

- **「21 个 pytest + 前端 5 个测试脚本」。**  
  现网：后端 `test_*.py` **24** 个；前端 `*.test.mjs` **7** 个（`package.json` 的 `npm test` 已列出）。CI 仍是 Python 3.12 + Node 20。

- **表 9（十一节，但源自同一工程量口径）「七十六个 Python 模块」** 与现网对不上。`backend/app` 约 56 个 `.py`，整个 `huicha-aml` 约 100 个。建议改成「后端应用模块五十余个」或删掉精确个数。

- **「可配置 DeepSeek/智谱/本地模型」**：本地模型没有专用推理服务，只是 OpenAI 兼容 HTTP；无密钥走 stub。不要写「已接行内私有化」。Judge 工具补证（`HUICHA_JUDGE_TOOLS`）**默认关**，不要写成产品默认能力。

- **知识库**：不要停在「16 篇作业口径」。另有法规章节（反洗钱法、CDD、UBO、大额可疑等），`GET /api/health` 的 `kb_docs` 为目录篇数（约 38），检索单元更多。检索仍是关键词 + 字符 TF-IDF，**不是向量 RAG**——这一句 v4.1 已写对，保持。

## 第六节　核心创新与技术壁垒

### P0　创新表述与实现差一层

- **「判断可审计」只写了编号契约，漏了现网已上的可执行谓词。**  
  `judge_v3p` 要求交易模式理由带封闭谓词，后端在流水快照上重跑（`predicates.py`）。假编号仍整份失败；谓词失败走修复轮 / 弃权，不一定再「整份一票否决」（`verify_judge` 对已核验主张有放宽）。第六节第 2 点应补谓词，并删掉过绝对的「整份建议校验失败」——改成「硬契约失败则不可直接同意签发」。

- **「Skeptic 反事实核验」写成每次都重跑、失败建议不得签发。**  
  仅当契约已通过且存在 `supporting_evidence_ids` 才跑有界搜索（最多 4 候选 / 3 轮）。覆盖率机制实验约 **59.8%**，不是 100%。反事实输出无效时 `faithful=null`，**不得说成「结论没变所以模型在胡说」**。系统弃权 ≠ 改档。

- **「规则与 AI 不加权」正确**，但不要再提旧 Challenger `delta` 调分。`assemble` 里 `llm_delta=0`、`scoring.mode=judge_not_additive`。`risk.aggregate` 仍留着旧注释，答辩不要引用该函数当现行公式。

- **「先安全再智能」里的双人签发**：与屏幕文案对齐为「提交复核 / 同意签发 / 修改后签发 / 退回」，不要用旧稿「采纳 / 修改后采纳 / 驳回」单独当主按钮名（`modify` 仍存在，但是复核岗的「修改后签发」）。

- **事实回查**：虚构账号演示 token 是 `6222-FAKE-9999`。硬拦截的是工具事实表里没有的账号/编号；「约五万元」等是软放行。不要说「所有金额都必须等于某笔流水」。

### P1　8 号文映射表（表 5）容易夸大

- 「分类分级」：代码只丢 `city/phone/id_number` 等准标识并做出站脱敏，**没有**行内数据分级体系。建议改成「出站脱敏 + 准标识丢弃（竞赛原型）」。  
- 「全生命周期管理」：有工具审计与签发人留痕，**没有**模型卡、再训练流水线、生产变更管理。建议改成「调查过程可回放、签发可追责」。  
- 「防数据投毒」：只有只读白名单与确定性抽数，不是投毒对抗训练。  
- 「供应链自主可控」：网关可换厂商，**不是**已完成行内私有化。  
- 知识库 playbook `KB-PROC-01` 仍写 Challenger 抗辩，不要当 8 号文「已落地」引用。

### P2　差异化表（表 6）

- 「规则引擎类智能调查」一行可用，但须加：规则对照仍会打出自己的三档，工作台并排展示，**分歧交给人**，不是规则消失。  
- 智盾链一行保持「不比检出」即可；不要写成已与某产品联调。

## 第七节　效果验证

### P0　数字与产品默认 prompt 必须拆开

- **不要把盲区 `judge_v4` Macro-F1 0.994 写成「慧查的准确率」或「当前系统成绩」。**  
  产品默认是 `judge_v3p`（带谓词）。0.994 是 `enrich_judge` 直调、`prompt=judge_v4`、合成盲区集、计分 215/220（5 条解析失败未计入混淆矩阵）。  
  建议现场口播只用：「同一模型换提示词，排除档不再全被打成观察」；必须报数时带齐 **数据集名 + prompt 名 + 合成金标 + 须人签**。

- **图 5 读法与正文 7.2 不是同一组数。**  
  正文写盲测保留集 `judge_v4` 0.994；图注写盲测由约 0.43 升至约 0.93——那是 **盲区上 v2→v3**（0.4259→0.9286）。两套数都对，但必须标注，禁止并成一条曲线。

- **开发集 0.39→0.97 请用报告原值并标明集名。**  
  `REAL_MODEL_REPORT.md`：`judge_v2` 0.3867 → `judge_v3` 0.9662，集为 `narrative_vignette_v3_rules_layer` n=240。四舍五入成 0.39/0.97 可以，但必须写「合成开发集、例举类型学与测试族重合，条件乐观」。

- **机制验证（表 7）与真实模型消融混排时，要写清 stub vs 真模型。**  
  100% 拦截 / 0% 干净误报 / 100% 引用契约 / 59.8% 反事实覆盖 = **stub 全流水线**。0.97 / 0.994 = **真模型、只跑 Judge 契约**，不经过 Reporter、双控、出站脱敏工作台路径。禁止说「流水线 Macro-F1=0.99」。

- **「引用契约通过率 100%」在真模型表里是 `verify` 通过率，且不计 parse_failures。**  
  盲区 v4：parse_failures=5。不要说「220 条全部合法 JSON」。

- **证据 P/R 0.777/0.967 只在叙事项 `IX-` 上计算**，TX-/KB- 引用另计。不要说成「全部证据编号语义正确」。

- **v1/v2 集已降级（标签泄漏），禁止与 v3 混比或写成「从 0.17 提升到 0.97」。**

### P1　工程质量与诚实边界

- 测试文件数见上（24+7），「21+5」要改。  
- 「真实脱敏 hold-out 是 P0 待办」正确；`real_holdout.json` 仅为占位，不要写已评测。  
- 人效：`efficiency_records.csv` 仍空。第七节已声明不写效率%，**全文其它节（摘要、落地、特点）也不得出现「提效 xx%」或未测的「缩短追赃时间」。**  
- `experiments/ablation.py` 的 A–E 变体仍是 `Not evaluated yet`，不要当消融结果表。

### P2　口径句建议（可直接替换 7.0 段）

> 机制验证（stub、完整流水线）证明事实回查、引用契约、反事实路径可复现；独立合成集上的真实模型消融证明：同一模型下，把三档可操作标准写进 Judge 契约后，排除/上报不再塌成观察。两组数字都不是生产调查准确率。产品默认 prompt 为 `judge_v3p`；`judge_v4` 的 0.994 仅属于盲区消融，不得简称准确率。Agent 建议须经调查员提交、复核岗签发。

## 第五节–七节之外、但会从技术页漏到口头的旧句

（评委对照工作台时最常见，建议技术页同步删）

| 旧句 | 现网 |
|------|------|
| 人点「签发结论 / 采纳」 | 调查员「提交复核」，复核岗「同意签发」 |
| 最终状态「已报送」 | `ready_to_file` / 已签草稿 |
| 默认 Judge = v3 或 v4 | **v3p** |
| 准确率 97% / 99.4% / F1=1 | 禁止 |
| 已接核心 / SSO / 企业级 RAG / 联邦学习 / 自动报送 | 禁止 |

| Challenger 调分合成结论 | 已废弃；现名为「慧查 agent」开关 |
| 去掉模型后系统同等可用 | 只剩规则对照 + 模板骨架 |
